# 技能手册

八个技能，都在 `.agents/skills/`。每个技能是一个 `SKILL.md`，含 YAML frontmatter
（`name` + `description`）和正文规则。**`description` 决定它什么时候被自动加载**，
所以要写清触发场景。

```
.agents/skills/
├── ai-content-ops/          总纲与统一入口（认意图 → 路由 + 红线 + 工具地图）
├── ai-topic-scout/          选题
├── ai-article-writer/       写作
├── ai-title-optimizer/      标题
├── ai-article-formatter/    排版
├── ai-wechat-publish/       发布
├── ai-data-analyst/         复盘
├── writing-voice/           文风
└── _shared/
    └── account-status.template.md
```

---

## 怎么用（两种方式）

**方式一：自然语言（推荐）**
直接说「今天有什么选题」「选题3」「写这篇」「起标题」「排版」「发布草稿箱」「复盘」，
`ai-content-ops` 会路由到对应技能。

**方式二：直接点名**
说「用 ai-article-formatter 排版这篇」，跳过路由。

---

## `ai-content-ops` — 总纲与统一入口

**触发**：任一环节指令，或"不清楚该走哪个流程"。

**它做什么**
- **认意图 → 路由**：一张表把用户的话映射到子技能与交付物
- **跨阶段红线**：零编造 / 禁匿名信源 / 禁配图提示 / 合规三件套 / 无素材不写实测
- **工具地图**：哪个环节该跑哪个脚本（机械活一律走脚本，别手工翻文件）
- **文件地图**：风格卡 / 账号状态 / module-log / 上下文 各管什么

**两条设计原则**
1. **一次只走一个环节**。用户说"今天有什么选题"就只做选题，不顺手写稿。
2. **不自动往下跑**。每环都有用户的判断（选哪个题 / 素材够不够 / 风格对不对）。

## `ai-topic-scout` — 选题

**触发**：今天有什么选题 / 扫一轮 / 有什么深度话题。

**交付物**：5–8 个选题卡（分国内外两组，各组至少 2 个）+ 搜索验证 + 优先级建议表。

**开工第一步永远先跑脚本**

```bash
python3 tools/topic_scan.py --hours 48 --top 12 --demand "核心词1" "核心词2"
```

**评分表（0–14 分）**

| 维度 | 分值 | 标准 |
|---|---|---|
| 热度 / 时效 | 0–2 | 24–48h 内 = 2；7 天内 = 1 |
| 信息增量 | 0–3 | 有没有别人没有的角度 / 数据 / 可实测路径。**纯转述 = 0** |
| 与 AI 的相关性 | 0–2 | 是不是一件与 AI 相关的真事（不为赛道加分） |
| 争议 / 讨论度 | 0–2 | 有没有可站队的立场空间 |
| 信源可验证 | 0–2 | 能否凑齐 2 个独立信源（官方一手优先） |
| 搜索价值 | 0–3 | 用 `search_demand.py` 实测：≥2 个具体长尾 = 3 |

**分级**：≥11 🔥优先｜8–10 ✅可做｜5–7 ⚠️备选｜<5 ❌不做

**每个选题卡必须回答**

> **这件事改变了什么旧规则？**

答不出来 = 纯资讯，直接排除。这是整套系统的选题第一性标准。

**降级规则（固定，不临场判断）**：够标准的不足 5 个时，直接说「今天高质量选题较少」，
给最高分 2–3 个 + 1–2 条可快速发布的短资讯，并标注这是降级输出。

## `ai-article-writer` — 写作

**触发**：选题X / 写这篇 / 开始写。

**开工第一步**

```bash
python3 tools/draft_kit.py brief    # 一屏读完所有硬约束与去重清单
```

**第一步永远是判断素材状态**

| 状态 | 条件 | 体裁 |
|---|---|---|
| **A** | 用户给了截图 / 录屏 / 数据 / 操作记录 / 口述体验 | 实测型：可写亲身体验，细节必须可回溯 |
| **B** | 没有实测素材（**默认**） | 分析型：**禁止任何亲历式描述和体验性数字** |

状态 B 若用户要求实测 → 先交【实测脚本】（测什么 / 几个维度 / 记哪些数字 / 预计耗时），
拿到素材再补写；文末必须注明「**本文未做实测**」。

**禁止句式**：我测了 / 我跑了 / 大概花了半小时 / 效果比之前好不少 / 实测下来很丝滑。

**六模块结构**（功能固定、表达不固定）

| 顺序 | 模块 | 要求 |
|---|---|---|
| 1 | 核心判断开篇 | 一段话说清核心观点，先给判断不绕弯 |
| 2 | 事件背景 | 只交代事实，**不超过全文 20%** |
| 3 | 分层拆解 | 2–4 个小标题，每层有数据 / 案例 / 对比支撑 |
| 4 | 行业对照 | 与国内外同类事件、路线、模式对比 |
| 5 | 深层变化 | 对行业规则、竞争格局、创作者生态的结构性影响 |
| 6 | 结论 | 回扣核心判断，给一句可传播的金句 |

⚠️ **功能固定 ≠ 表达固定**：小标题措辞与切入顺序**每篇必须不同**。
篇篇同构会形成段落指纹，触发同质化判定——比结构不完整更致命。
写作前查 `module-log.md` 最近 5 篇，本篇不得重复。

**判断力的硬要求**
- 每层拆解必须有判断，不能只复述新闻（但不必每段都上价值）
- 至少有一处"别人没说的观点"或"别人没做的对比"
- 判断必须落在证据上（数据、官方原文、对比表），不能是"我觉得"

**写完必附排版交接单**：核心数字清单（3–6 个，注明出处）/ 建议配图位（3–5 个）/ 金句一句。

## `ai-title-optimizer` — 标题

**触发**：起标题 / 优化标题。

**硬规则**：16–25 字｜核心词在**前 15 字**内（搜索结果只显示前 15 字）｜必带 Emoji｜
必含具体数字或「实测/对比/体验」｜同一核心词只出现 1 次｜禁止纯情绪标题。

**禁止把内容说完**：数字要指向**结果**，不要指向**结论**。
"X 换了条路"可以；"X 换了 A 路所以以后 Y 会消失"不行。

**输出**：8 个候选，每个按「搜索权重」「点击吸引力」双维打分（0–10），
另附一个**最稳妥版**（搜索权重最高）和一个**最强传播版**（情绪钩子最足）。

## `ai-article-formatter` — 排版

**触发**：排版 / 准备发布。**只管呈现，不改内容**——发现内容问题只标注，改写要回写作环节。

**移动端硬规则**：单段 ≤65 字（约 4 行）｜段落之间空一行｜连续 3 段以上等长要把中间段拆开。

**小标题必须用 `## 一、xxx`**：md2wx 靠它渲染成胶囊；不要用 `▍` 等花式符号。
两个小标题间距 ≤600 字。

**加粗是稀缺资源**：全文 ≤8%｜每次只包一个关键词或数字｜一段最多 1 处｜优先加粗数字与结论词。

**引用块只用于两类**：官方原话（带出处）、全文金句。

**配图**：每 350–500 字一张；**用 `![图注](路径)` 语法**，绝不写"此处放图"这类占位文字
（渲染器会把它当正文渲染出来）。优先用 `tools/make_figs.py` 的模板生成。

**交付**：符合 md2wx 语法的 markdown 稿 + 一份发布后人工操作清单。

## `ai-wechat-publish` — 发布

**触发**：发布草稿箱 / 推送到草稿箱。

**默认走一条命令，不要手工分步执行**

```bash
python3 tools/wx_publish.py formatted/xx-排版稿.md --tag 深度解读
```

**前置条件**：preflight 退出码 0（脚本内置）。
**凭据**：`WX_APPID` / `WX_APPSECRET` 放 `~/.workbuddy/.env`，**绝不写进技能文件、绝不回显**。

**改排版 = 只改样式不改字**：必须做字符级核验，中文 / 字母数字 / emoji 三段序列
必须完全一致（脚本第 ④ 步内置）。三个已知假阳性：`<br>` 要先还原成换行再剥标签；
md 侧要先剥 YAML frontmatter；加图后要同时剥 md 的 `![](...)` 与 HTML 的 `<img>`。

**发布后必做**：写每日日志 → 有账号数据更新就同步 `account-status.md` → 发完一篇在
`module-log.md` 追加一行（小标题与切入角度）。

## `ai-data-analyst` — 复盘

**触发**：分析数据 / 复盘 / 粘贴广告数据表格。

**最关键的一条规则**：**基线为空时只记录、不下结论。**

指标算不出来就写"算不出"，并说明缺哪个字段；能推算的要写明推算过程。
不把收入回升当成内容质量改善的证据（广告收入主要跟曝光存量相关）。

## `writing-voice` — 文风

**触发**：太AI化 / 不像我写的 / 优化文风 / 需要校准个人口吻。

**四轮流程**：收语料 → 对照诊断 → 边界追问 → 盲测。

**产出「风格卡」**（`voice/风格卡.md`），十个字段：句长 / 人称 / 标点习惯 / 开场方式 /
收尾方式 / 情绪档位 / 口语词表 / 禁用词表 / 举例习惯 / 典型段长。

**建卡方法**：把 3–5 段用户自己写的文字放进 `voice/语料/`，跑

```bash
python3 tools/voice_check.py --corpus voice/语料 --save voice/基线.json
```

**关键：风格卡是硬约束，不是参考。** 卡里写「不用」的东西一处都不许出现。
改卡规则：**只有用户明确说"以后就这么写"才改**，每次改动在末尾记「日期 + 改了什么 + 为什么」。

一个踩过的坑：**微信口述语域不要整体迁移到文章**。用户口述里"你"很密集（50+/千字），
但那是口语场景；写文章时不密集用"你"是刻意选择，盲测确认过的。
